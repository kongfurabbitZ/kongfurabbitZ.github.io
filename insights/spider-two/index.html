Spider 2.0 为什么让企业 SQL 题变难了？

真实的数据问题往往得先找表、读文档、理解代码，再写查询。

真实的数据问题往往得先找表、读文档、理解代码，再写查询。Spider 2.0 把这些步骤一起纳入评测，使失败原因可以沿整个工作流程追溯。

研究方法与证据

维度评估
数据 / 来源作者先收集 74 个 BigQuery、54 个 Snowflake、30 个 SQLite、40 个 DuckDB、10 个 PostgreSQL 和 5 个 ClickHouse 数据库，并从教程、论坛和项目中收集 1,021 条复杂 SQL 与 157 个转换项目，最终保留 547 条 SQL 和 78 个 DBT 项目。来源确有真实应用痕迹，但主要是公开数据、Marketplace、教程和开源项目，不等于企业内部生产工作负载。
样本与边界Spider 2.0 有 632 个任务、213 个数据库；lite 与 snow 各 547 个任务。筛选要求 SQL 超过 50 tokens，并确保改写后成功执行、运行时间可接受且返回非空结果。这提高了可评测性，却系统性排除了空结果、超时、脏数据和失败恢复等真实运维情境，也偏向复杂长查询。
变量 / 测量Spider 2.0 用任务成功率；lite 和 snow 用 focused execution accuracy，只要求 gold 结果的关键列出现在预测结果中，并可忽略其他列与顺序。它降低了未指定输出列造成的假阴性，但也可能接受带有多余、敏感或业务上不应出现字段的结果。作者称红队测试未增加假阳性，却没有报告红队样本规模、错误率或独立复核统计。
识别或评估策略同时比较多个模型、代码代理和 Text-to-SQL 方法，并按难度、嵌套列、文档、DBT、数据库类型拆分。证据足以证明“在这套任务与 harness 下性能低”，但无法单独识别低分来自基础模型、检索与 schema 过滤、行动接口、prompt、上下文裁剪还是预算限制。

结论的适用条件

批判维度具体问题对结论的影响
隐性假设公开数据应用、技术教程和开源 DBT 项目能代理企业内部任务分布；SQL token 长度能作为主要难度分层；gold 结果和 focused matching 能代表业务正确性；表层和语义重写足以缓解训练污染。不推翻 benchmark 的挑战性，但会限制“真实企业”与“无泄漏”的强表述。
替代解释BigQuery 未做 value linking、超长输入从开头截断、schema 过滤与工具设计不成熟，可能是低分的重要来源；代理法的较高分也可能主要来自执行反馈和更多上下文，而非更强推理范式。结论应从“模型不行”改写为“当前模型加上下文基础和 harness 组合不够可靠”。
可反证路径在时间隔离、独立企业抽样的新任务上复测；引入高质量语义层、值链接和检索后固定模型与预算；由独立评审给出多种合法 gold 并审计 false positive；对随机代理运行报告多种子置信区间。如果简单的上下文基础改进就使性能大幅跃升，论文关于模型推理缺陷的解释会被削弱；如果独立企业样本更简单，“普遍企业鸿沟”的外推会收缩。

值得继续追问

  1. 怎样区分找错业务对象、写错查询和评测脚本无法识别等价答案？
  2. 如果固定同一个模型、相同 token 与执行预算，只依次加入值链接、语义层、schema 检索、方言编译和项目级记忆，Spider 2.0 的增益曲线会如何变化？哪一层才是真正杠杆点？
  3. 如果按企业真实任务频率而不是“复杂案例优先”抽样，并把空结果、权限失败、数据延迟、脏数据和回滚纳入成功定义，结论会变强还是变弱？
