Enterprise Ontology 用一套共同词汇描述企业活动，使参与者可以核对模型里的承诺。应用时需要检查定义能否支持跨部门共同推理，以及为此增加了多少维护工作。

研究方法与证据

维度评估
数据 / 来源主要来源是 Enterprise Project 的项目交付、术语定义、Ontolingua 形式化过程、工具集实现和应用案例。它的证据是工程过程证据，而不是实验数据。
样本与边界样本边界集中在 Enterprise Project 及相关企业应用，包括 Pilkington Optronics、IBM Market Analysis、Lloyds Register CPI 等。外部泛化需要谨慎。
变量 / 测量没有量化变量。论文用“是否降低歧义、是否可复用、是否支撑工具集、是否便于人类理解”等工程判断作为评价口径。
识别或评估策略采用实际用途与原始目的对照：人类沟通、稳定需求基础、工具互操作、工具集自举开发。这个评价框架清楚，但不是因果识别。

结论的适用条件

批判维度具体问题对结论的影响
隐性假设假设企业中存在可被跨团队接受的核心概念集合，且共享定义能降低沟通成本。大体成立，但在高度政治化或局部术语强绑定的组织里，定义共识可能被权力关系和部门边界削弱。
替代解释Market Analysis 成功可能更多来自使用者熟悉本体方法，而不是 EO 本身质量更高。说明本体收益依赖人员能力和方法体系，不能把成功完全归因于术语定义。
可反证路径如果在多个企业项目中，提供同等图形化工具和训练后，本体组仍不能减少误解、需求返工或工具集成成本，则本文关于共享语义价值的主张会被削弱。会削弱本体作为企业建模基础设施的实践价值，但不必然推翻其概念分析价值。

值得继续追问

  1. 两项活动共用一个名称却有不同目标时，模型如何表达差异？
  2. 一个人同时承担多个角色时，模型能否区分身份与责任？
  3. 如果两家企业使用不同时间尺度，活动模型能否共用？
