Shift-Up 尝试让行为示例、架构图和决策记录成为生成与检查代码的依据。值得验证的是，这些工程制品究竟在哪些改动中减少了偏离设计的返工。

研究方法与证据

维度评估
数据 / 来源研究对象是一个在线 snack-bar full-stack web app，涉及 GUI、PostgreSQL、admin system 和 backend logic；初步分析 176 条 prompt。
样本与边界单一应用、单一研究设置、初步结果；适合形成设计知识，不足以证明普遍效果。
变量 / 测量关注 Agent autonomy、drift、traceability、prompt pattern、upfront investment、automated validation。
识别或评估策略比较三种开发范式，但不是随机实验；更像探索性设计科学评价。

结论的适用条件

批判维度具体问题对结论的影响
隐性假设BDD、C4、ADR 能被及时、准确、低成本维护；Agent 能理解并遵守这些制品；自动测试能覆盖关键行为。若制品维护成本高或质量低，Shift-Up 可能变成“高仪式感的慢流程”。
替代解释改善可能来自开发者更认真地思考需求和架构，而不是制品被 Agent 使用本身。会削弱“机器可读护栏”的独特贡献，但仍支持结构化开发前置。
可反证路径若在多个复杂项目中，Shift-Up 与结构化 prompt engineering 的质量差异不显著，而前置成本更高，则框架需要收缩到高风险或高复杂场景。会把 Shift-Up 从通用流程变成场景化治理方法。

值得继续追问

  1. 一次需求变化后，如何识别已过期、会误导代码生成的决策记录？
  2. 对企业内部 AI 生成应用，哪些制品是最低必要护栏，哪些会变成过度流程？
  3. BDD、C4、ADR 如何转成 Agent 可直接消费的上下文格式和版本策略？
